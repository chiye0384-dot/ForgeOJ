# ForgeOJ 决策日志

> 状态：已确认的架构与产品决策。  
> 基线日期：2026-09-24。  
> 注意：决策被接受不代表功能已经实现。

## 1. 使用方式

每个决策包含背景、结论、原因和代价。后续只有在出现安全问题、事实证明不可实现或用户明确变更需求时才修改；修改时保留旧结论并新增记录，不覆盖历史。

状态取值：`ACCEPTED`、`SUPERSEDED`、`REJECTED`、`DEFERRED`。

## 2. 已确认决策

### D-001：项目名称使用 ForgeOJ

- 状态：`ACCEPTED`
- 结论：项目使用独立名称 ForgeOJ，不沿用 CodeJudge，也不使用过于泛化的 Java Online。
- 原因：形成独立项目身份，避免让简历产生“换名复刻”的印象。
- 代价：需要自行建立品牌、页面和文档体系。

### D-002：选择有挑战但可解释的在线判题方向

- 状态：`ACCEPTED`
- 结论：Java 简历项目选择在线判题与小班教学平台，而不是更稳妥的点评或预约系统。
- 原因：异步判题、沙箱和可靠消息链路有区分度，且范围仍可控制。
- 代价：安全、Linux、Docker 和故障处理的学习成本更高；必须分阶段开发。

### D-003：不追求功能堆叠和伪造复杂度

- 状态：`ACCEPTED`
- 结论：不为了简历名词引入 Spring Cloud、Gateway、Kubernetes、XXL-JOB 或多语言。
- 原因：单机小规模项目不需要这些基础设施，无法解释的技术只会增加失败面。
- 代价：简历上的技术名词更少，但每项能力需要有更深证据。

### D-004：V1 使用 JDK 21

- 状态：`ACCEPTED`
- 结论：后端和用户代码运行环境均固定为 JDK 21。
- 原因：JDK 21 是长期支持版本；统一版本能减少判题差异并便于固定镜像。
- 代价：用户不能自行选择其他 JDK；以后扩展版本必须做镜像和题目兼容治理。

### D-005：V1 仅支持单文件标准输入输出题

- 状态：`ACCEPTED`
- 结论：源码为无 `package` 的 `Main.java`，仅使用 JDK 标准库。
- 原因：先把可靠、安全的判题链路做深。
- 代价：不支持 LeetCode 式函数题、多文件工程和第三方依赖。

### D-006：API 与 Judge Worker 隔离

- 状态：`ACCEPTED`
- 结论：API 服务不接触 Docker；独立 Judge Worker 执行代码。
- 原因：缩小 Docker 控制权限的暴露范围，并让业务请求与重任务解耦。
- 代价：需要消息契约、任务状态、幂等和独立部署。

### D-007：异步主链路使用 Outbox 与 RabbitMQ

- 状态：`ACCEPTED`
- 结论：API 在一个数据库事务内写 Submission 与 Outbox，由发布器投递 RabbitMQ，Worker 手动 ACK。
- 原因：避免“数据库已提交但消息丢失”，并能演示至少一次投递下的幂等处理。
- 代价：存在最终一致窗口，需要重试、死信、补偿和运维页面。

### D-008：数据库是最终事实来源

- 状态：`ACCEPTED`
- 结论：MySQL 保存权威业务状态；Redis、Elasticsearch 和 WebSocket 都不是事实来源。
- 原因：缓存、索引和推送都可能失效或重建。
- 代价：所有读取优化和降级都必须回到数据库进行可见性与权限复核。

### D-009：一次提交使用一个全新容器

- 状态：`ACCEPTED`
- 结论：每次正式提交新建容器，编译一次，每个测试用例启动新 JVM，首个失败即停止。
- 原因：隔离不同提交，并避免测试用例之间的静态状态污染。
- 代价：吞吐低于常驻沙箱；需要记录创建、执行和清理开销。

### D-010：Docker 沙箱是受控边界，不宣称绝对安全

- 状态：`ACCEPTED`
- 结论：采用非 root、禁网、只读根文件系统、能力删除和资源限制等措施，只做小范围受控试运行。
- 原因：普通容器不能等同虚拟机或专业沙箱，不应夸大安全性。
- 代价：不开放匿名提交，不承诺安全运行互联网中的任意恶意代码。

### D-011：平台故障和用户判题结果分离

- 状态：`ACCEPTED`
- 结论：处理状态与 AC/WA/CE/RE/TLE/MLE/OLE/SECURITY_VIOLATION 分开，平台错误使用 SYSTEM_ERROR。
- 原因：不能把 Worker、Docker 或基础设施故障归咎于用户程序。
- 代价：状态机和重试规则比单一状态字段更复杂。

### D-012：隐藏测试不向普通用户泄露

- 状态：`ACCEPTED`
- 结论：用户看到结果和必要错误，但看不到隐藏输入、正确输出、测试编号或通过数量。
- 原因：隐藏测试用于验证边界条件，泄露后可被硬编码绕过，破坏判题有效性。
- 代价：错误信息需要在可诊断性和保密性之间取舍。

### D-013：正式题目必须有私有参考程序和官方题解

- 状态：`ACCEPTED`
- 结论：参考程序用于验证测试数据；官方题解面向学习者，两者独立存储。
- 原因：只给对错而不给学习出口不符合平台定位。
- 代价：出题和审核成本增加；判题版本变化后必须重新验证题解。

### D-014：公共题解可提前查看，班级题解由作业控制

- 状态：`ACCEPTED`
- 结论：公共题未 AC 时经防剧透确认可查看；班级作业支持立即、AC 后、截止后开放。
- 原因：公共自学和课堂教学的约束不同。
- 代价：需要保存开放策略和个人查看记录。

### D-015：班级角色按班级作用域分配

- 状态：`ACCEPTED`
- 结论：使用 OWNER、ASSISTANT、MEMBER；一个用户在不同班级可有不同角色。
- 原因：助教是班级内协作角色，不应提升成全站权限。
- 代价：所有班级接口都必须验证资源归属和当前成员状态。

### D-016：平台管理员是独立身份域

- 状态：`ACCEPTED`
- 结论：CONTENT_REVIEWER、OPS_ADMIN、SUPER_ADMIN 使用独立账号和后台，不参与普通做题与班级。
- 原因：内容审核、故障处理和普通用户行为职责不同，降低越权和误操作风险。
- 代价：需要独立认证、权限矩阵、初始化流程和审计日志。

### D-017：任何普通用户都可创建班级

- 状态：`ACCEPTED`
- 结论：不核验真实教师身份；创建者成为 OWNER，成员通过邀请码加入。
- 原因：产品面向学习小组，不是学校教务系统。
- 代价：不能把 OWNER 对外宣称为学校认证教师。

### D-018：个人题单 V1.0 与 V1.1 仅私有

- 状态：`ACCEPTED`
- 结论：V1.0 与 V1.1 的个人题单是私人学习计划，创建时默认且只能本人可见，不提供公开入口；公开题单进入 V2.0 候选范围。
- 原因：题单内容可反映个人兴趣和学习状态；公开后还需要举报、下架、作者注销、收藏/复制和公开主页等闭环，简历增益低于核心判题能力。
- 代价：V1.0 与 V1.1 用户不能分享自建题单。未来即使支持公开，也必须默认私有、由用户主动发布，并允许取消公开；公开列表不能暴露非公开题目。

### D-019：用户题解必须绑定自己的真实 AC 提交

- 状态：`ACCEPTED`
- 结论：V1.1 发布题解时，已验证代码只读；修改代码必须重新提交并 AC。
- 原因：防止“题解显示已通过，但发布后代码已被改坏”。
- 代价：编辑体验不如自由富文本，需要从提交创建作答副本。

### D-020：题解标题使用确定性模板兜底

- 状态：`ACCEPTED`
- 结论：标题最终必填，用户留空时生成《题目名称》题解；思路和复杂度选填。
- 原因：这是低失败率的确定性需求，不需要引入 AI。
- 代价：默认标题不个性化，但可由用户修改。

### D-021：评论最多三层

- 状态：`ACCEPTED`
- 结论：题解与题目讨论支持三层结构，继续讨论时新开根评论。
- 原因：覆盖提问、解答、感谢或补充，同时限制查询和界面复杂度。
- 代价：不适合无限延伸的长讨论；复杂讨论延后到综合论坛评估。

### D-022：公共内容审核分阶段实施

- 状态：`ACCEPTED`
- 结论：V1.0 公共题目发布前审核；V1.1 题解和评论先发布、后举报处置。
- 原因：题目会影响判题正确性，风险高于一般讨论内容。
- 代价：V1.1 必须有举报、软删除、恢复和审计闭环。

### D-023：Elasticsearch 只索引公共题目

- 状态：`ACCEPTED`
- 结论：ES 只存公共题目的可公开检索字段，故障时回退 MySQL。
- 原因：避免私有题和源码泄露，并保持索引可完全重建。
- 代价：班级私有题不享受全文搜索；降级时功能受限。

### D-024：最终验收必须在固定 Linux 环境

- 状态：`ACCEPTED`
- 结论：Windows/WSL2 可用于开发，最终功能、安全和性能验收使用固定 Linux 环境。
- 原因：Docker 资源控制、文件权限和脚本行为需要在目标系统验证。
- 代价：开发后期必须安排独立 Linux 验收周期。

### D-025：优先阿里云小范围上线

- 状态：`ACCEPTED`
- 结论：V1.0 接近完成后部署到 Linux 云服务器，邀请少量真实用户试用；不承诺公共大规模服务。
- 原因：真实部署能验证 HTTPS、配置、备份、监控和故障处理，比只在本机演示更有证据价值。
- 代价：产生云资源成本和日常运维责任；资源应在 M0 验证后再购买。

### D-026：不故意保留 Bug

- 状态：`ACCEPTED`
- 结论：不为了让面试官提问而制造缺陷；通过真实限制、取舍和后续改进提供讨论点。
- 原因：故意缺陷会破坏可信度，也可能变成安全和数据问题。
- 代价：需要认真记录选择原因、边界和未做事项。

### D-027：允许复用通用脚手架，不复制 OJ 核心

- 状态：`ACCEPTED`
- 结论：可复用许可证清晰的后台布局、基础认证和工程设施；判题域、Outbox、Worker 与沙箱链路重新设计实现。
- 原因：节省低价值搭架时间，同时保留核心能力的真实所有权。
- 代价：必须记录上游版本、许可证、修改点和第三方声明。

### D-028：只有有证据的 Release 能力才能进入简历

- 状态：`ACCEPTED`
- 结论：设计、计划和能启动均不算完成；功能需有代码、测试、报告和 release 对应关系。
- 原因：确保所有简历亮点可定位、可修改、可复现、可解释。
- 代价：简历内容会晚于代码出现，但可信度更高。

### D-029：采用最小官方生成骨架

- 状态：`ACCEPTED`
- 结论：后端使用 Spring Initializr 生成的最小工程作为起点，由 ForgeOJ 自建 Maven 根聚合工程及 `forgeoj-api` / `forgeoj-judge-worker` 边界；前端使用官方 create-vue 最小模板。不以 RuoYi-Vue-Plus、ruoyi-vue-pro、JHipster 或完整 OJ 系统作为底座。
- 原因：该方案许可证和来源可追溯，不带入无关业务、大型管理框架或其自有架构约束，也能保留 ForgeOJ 核心链路的真实所有权。
- 代价：通用认证、权限、异常和页面设施也需在后续里程碑中自行实现，不能直接声称脚手架的功能。

### D-030：后端基线使用 Spring Boot 4.1.1

- 状态：`ACCEPTED`
- 结论：在 D-004 的 JDK 21 基础上，新建后端固定使用 Spring Boot 4.1.1，不从已结束开源维护周期的 Spring Boot 3.5 起步。
- 原因：4.1.1 是确认时的稳定 GA，官方支持 JDK 17–26；已核验的 MyBatis 4.1.0 也明确面向 Spring Boot 4.1。绿地项目没有 Boot 3 迁移包袱。
- 代价：必须按 Spring Framework 7、Jakarta EE 11、Jackson 3 和 Boot 4 的细分 starter/测试包实现；以后引入的库都要单独验证 Boot 4.1 兼容性，不能照搬 Boot 3 教程。

### D-031：持久层使用原生 MyBatis

- 状态：`ACCEPTED`
- 结论：直接使用 `org.mybatis.spring.boot:mybatis-spring-boot-starter:4.1.0`，不引入 MyBatis-Plus。API 和 Worker 都可使用 MyBatis，但两个可执行模块不得相互依赖。
- 原因：与用户已学的 SQL/Mapper 方式一致，能显式表达 Outbox、任务领取、状态条件更新和幂等 SQL，也避免为脚手架适配额外学习 MyBatis-Plus。
- 代价：通用 CRUD、分页和批量操作需要更多显式 SQL 与测试；这些是有意保留的可解释性。

### D-032：PageHelper 暂缓引入

- 状态：`DEFERRED`
- 结论：M-1 不引入 PageHelper，到 M2 实际出现题库、提交历史等列表查询时，再根据分页语义、`count` 成本、复杂 SQL 和 Boot 4.1 兼容版本重新过依赖门禁。
- 原因：PageHelper 很便利，但当前还没有任何列表 Mapper；现在加入只能证明依赖存在，不能证明分页行为正确。
- 代价：M2 第一个分页查询前需要一次专门评估和集成；本决策不是永久拒绝 PageHelper。

2026-10-03 首个公共题库分页已专门评估：固定 ID 排序、ACTIVE/当前版本条件和 EXISTS 标签筛选，由原生 MyBatis 明确执行 COUNT、LIMIT/OFFSET 及页内标签批量查询，可重复读事务保持同页统计一致。当前没有需要分页拦截器解决的复杂查询；本轮不增加 PageHelper，状态继续 DEFERRED。页大小上限 50，正整数页码转 long 偏移；这不代表深分页或 COUNT 已经通过性能验收。评估和验证范围见 [剩余 M2 实施计划](M2-REMAINING-IMPLEMENTATION.md)。以后采用 PageHelper 时仍需固定版本、许可证与实际 Boot 4.1 集成证据。

### D-033：使用主干加短期主题分支

- 状态：`ACCEPTED`
- 结论：`main` 是唯一长期集成分支并保持可构建；日常改动使用短期 `feat/*`、`fix/*` 或 `docs/*` 分支，通过审阅和 CI 后合入，不设置长期 `develop` 分支。里程碑只有在门禁通过后才打 tag。
- 原因：当前由个人学习和小规模协作推进，双长期分支会增加同步成本；短期分支仍能保留审阅、回滚和 CI 证据。
- 代价：远程 `main` 已启用分支保护并要求 `backend`、`frontend` CI；M0 起日常改动必须在短期主题分支完成并经 PR/CI 合入。

### D-034：ForgeOJ 自有代码采用 Apache-2.0

- 状态：`ACCEPTED`
- 结论：池也拥有版权并有权许可的 ForgeOJ 自有源代码采用 Apache License 2.0，版权声明为 `Copyright 2026 池也`。根 `LICENSE` 使用未修改的官方许可证全文，根 `NOTICE` 记录项目版权与需保留的第三方归属。
- 原因：Apache-2.0 是许可证边界清楚、允许宽松复用且包含明确专利授权的 OSI 批准许可证；它适合公开、可解释的学习项目，也满足 MySQL Universal FOSS Exception 对 “Other FOSS” 许可证类别的前提。
- 代价：他人可在遵守许可证的前提下商用、修改和形成闭源衍生版本；分发时必须提供许可证、标明修改并保留适用的版权、归属和 NOTICE。该决定只覆盖池也有权许可的部分，不会重新许可生成文件、保留的上游代码、依赖、题目内容或用户提交；正式发布物仍需完成第三方许可证审计。

### D-035：M0 使用 Docker CLI 沙箱适配器

- 状态：`ACCEPTED`
- 结论：M0 的 Judge Worker 通过 ForgeOJ 自有接口封装 `ProcessBuilder(List<String>)`，调用宿主机官方 Docker CLI 控制一次性判题容器；不把 `docker-java` 作为生产沙箱客户端。调用不经过 shell，不拼接含用户输入的命令，CLI 路径可配置且 Worker 启动时 fail fast 验证；API 进程不获得 Docker 权限。Testcontainers 仍会在 test scope 传递使用 `docker-java`，这不属于生产沙箱实现。
- 原因：已验证的 Docker CLI/Engine 具备 M0 所需的创建、限制、检查和强制清理能力，可避免在最小纵向切片中额外承担生产客户端 transport、Jackson、JNA 与 HttpClient 的兼容面；命令也能在开发和固定 Linux 环境独立复现。
- 代价：Worker 依赖宿主 Docker 可执行文件、当前 context 和 daemon；ForgeOJ 必须自行正确处理子进程并发输出、超时、输出上限、容器强制删除、临时目录清理与残留扫描。若后续证据显示 CLI 生命周期代码不可维护，再通过新决策评估类型化 Engine 客户端。

### D-036：M0 将输出超限持久化为 OLE

- 状态：`ACCEPTED`
- 结论：程序 stdout/stderr 合计超过提交快照中的输出上限时，Worker 终止执行并把结果持久化为 `OLE`。通过新增 Flyway V2 migration 扩展 verdict 约束，不修改已经执行过的 V1 migration；不得把 OLE 伪装成 `RE` 或平台 `SYSTEM_ERROR`。
- 原因：输出超限是用户程序触发的明确、可解释结果，且 V1.0 需求已经把 OLE 列为正式 verdict。独立结果能保持用户错误与平台故障的边界。
- 代价：M0 比原五种最小 verdict 多维护一种数据库枚举和自动化分支；未来若迁移到字典表或类型化状态模型，仍需保留历史 OLE 的兼容读取。

### D-037：排队取消采用动作接口而非删除资源

- 状态：`ACCEPTED`（2026-09-30 用户确认）
- 结论：使用 `POST /api/v1/submissions/{submissionId}/cancel`，只允许所有者取消 `QUEUED`，同一事务将 Task 与 Submission 置为 `CANCELLED` 并各递增一次版本；重复取消返回已有结果，保留 Submission、Outbox 与历史。
- 原因：取消是状态变化，不是删除提交；已发出的消息由 Worker 按数据库取消状态吸收，避免以删除消息或记录维持一致性。
- 代价：增加独立动作接口和受限列更新权限；必须验证 CSRF、越权隐藏、原子回滚、与 Worker 领取竞争及重复消息 ACK。

### D-038：允许一个运行槽位加三个排队任务，满队列重试保留槽位

- 状态：`ACCEPTED`（2026-09-30 用户选择“不预占排队名额”）
- 结论：按用户级 MySQL 锁串行检查配额。排队只计算 `QUEUED/RETRYING`，上限 3；运行槽位上限 1。平台失败时若排队已满，内部 Task 进入 `WAITING_RETRY`、清除执行租约并等待退避，对外 Submission 保持 `RUNNING`，继续占用原运行槽位。到期创建新 attempt；达到上限死信并释放槽位。队列未满仍按原 `RETRYING` 流程处理。
- 原因：用户明确要求运行时始终能排队三个；不能将失败任务直接加入已满队列形成四个，也不能因配额问题丢失重试。
- 代价：`RUNNING` 表示运行槽位已分配，不保证此刻正在执行用户程序；满队列重试等待期间同一用户后续任务不能运行。最多 3 个 attempt 与退避上限控制阻塞时间；主动恢复扫描必须启用。未来可另行评估更公平的调度，不能静默扩大排队上限。
- 数据边界：新增 V4 quota lock 表及既有账号回填，不修改已执行 V1/V2/V3；不向 Worker 授予账号表读取权限，也不向 API 授予修改源码、verdict、lease 或删除记录的权限。

### D-039：所有者同源 WebSocket 通知，GET 结果与轮询兜底

- 状态：`ACCEPTED`（2026-09-30 用户确认“采用这个合约”）
- 结论：新增 `/api/v1/submissions/{submissionId}/events`，沿用登录会话且仅本人订阅，严格同源；消息精确为 `submissionId/processingStatus/statusVersion`，不含源码、verdict 或诊断。前端不从推送渲染结果，而是按版本触发原 GET，断线后以轮询恢复。
- 原因：通知可以丢失或合并，MySQL 才是判题事实；复用现有资源所有者权限和原查询接口，使断线或旧消息不会改变真实结果。
- 代价：小规模实现以有界活动订阅的数据库采样发送已提交状态，而非可靠事件回放；重复/旧版本过滤，终态/登出清理，有限重连与轮询均须测试。当前进程内会话和连接上限限制多节点扩展，参见 L-029；不宣称通知逐状态必达或高并发容量。

### D-040：资源 verdict 使用内核增量证据，安全结果扩宽存储

- 状态：`ACCEPTED`（2026-10-02，在用户“继续下一步”的既有 M1 结果分类实施授权内落实）
- 结论：cgroup v2 每例前后可信计数中，PID max 增量归为 SECURITY_VIOLATION，局部 oom 增量归为 MLE；伪造 stderr、退出 137 和单独宿主 OOM kill 均不作为用户 verdict 依据。平台证据失败优先，其后 PID/MLE/OLE/TLE/RE/输出比较。用户资源结果不重试。
- 数据影响：V3 已允许两种结果，但 16 字符列存不下安全结果；V5 向后兼容扩宽到 32，不改已执行迁移，不新增授权。部署先迁移后 Worker。
- 边界：不是所有 Java OutOfMemoryError 或被拒的文件/网络操作都有可信内核事件，当前不根据不可信文本泛化判定。完整合约、失败处理、测试与限制见 M1 设计 5.3、L-032 和资源结果验证记录。

### D-041：普通账号采用短 JWT 与 MySQL 独立会话，邮件能力先闭环开发环境

- 状态：`ACCEPTED`（2026-10-02 用户确认“全部按你推荐的来，继续完成项目吧”）。设计接受与验证状态分别记录；普通账号单元现为 `VERIFIED`，完整 M2 保持 `IN_PROGRESS`，命令、源码/JAR 哈希与实际闭环见 [账号验收记录](M2-ACCOUNTS-VALIDATION.md)。
- 结论：新用户通过唯一用户名/邮箱和 BCrypt 密码注册，用户、quota lock 和激活令牌摘要同事务创建；`PENDING_VERIFICATION` 邮箱激活后进入 `ACTIVE`，`DISABLED` 不可邮件重新激活。旧 ID、密码、状态、配额和历史保留，旧 ACTIVE 可用户名登录，验证补邮箱后再开找回。
- 认证：访问 JWT 最长 5 分钟，每次登录建立绝对期限 7 天的 MySQL session；每个受保护 HTTP 请求校验签名/issuer/audience/期限并查询账号与会话，敏感写再次在事务内检查。Refresh 为随机 256 bit，仅存 SHA-256 摘要，单次轮换，重用撤销当前 sid；其他设备会话保持独立。全部退出、改密、重置和停用撤销全部旧会话，密码变化使旧重置令牌失效。
- 浏览器与通知：访问/refresh 使用 host-only、HttpOnly、SameSite=Strict Cookie，生产 Secure；所有写同时校验精确 Origin 和 CSRF，身份变化轮换 CSRF，refresh 保留 CSRF。凭据不进入业务 JSON、localStorage 或 URL。D-039 的 WebSocket 路径、owner/Origin、三字段、单调版本和轮询保持，认证改为 sid 并复核 MySQL；事务提交后的撤销关闭订阅，数据库扫描兜底，DB 异常关闭。
- 邮件与提示：激活 24 小时，重置/补邮箱 30 分钟，随机单次令牌仅存摘要；链接 fragment 由页面读取后清地址，POST 消费。注册/重发/找回统一 202 模糊提示，登录失败统一 401，无效/过期/已消费令牌统一 400。发信在提交后，开发模拟器仅 dev/test、loopback、有界内存，默认关闭，无真实 SMTP 和持久投递保证；失败可重发。
- 数据与权限：追加 V6，不修改 V1–V5；API 仅增加账号 INSERT、必要列 UPDATE 和认证表最小权限，Worker 不读用户或认证表；不改变 MQ 四字段、判题快照或 API 无 Docker 边界。
- 原因：保留 MySQL 权威会话与即时撤销，避免仅凭未到期 JWT 放行；与已验证判题/通知兼容，先使普通学习者注册到 AC 的开发链路可审查。Spring Security JOSE 提供 JWT 编解码，账号模型、状态、锁序、权限和流程由 ForgeOJ 实现。
- 代价：受保护请求增加 DB 查询；refresh 响应丢失或跨标签竞争后可能重新登录；进程限流重启不保留，数据库邮件冷却仍保持。开发邮件不证明真实 SMTP、云部署或可靠投递，Redis 缓存/分布式限流留 M4。升级后旧进程会话需重新登录；短 JWT 密钥必须外部配置，dev 临时密钥会在进程重启后变化。详细参数、四个验证单元及剩余边界见 `M2-ACCOUNTS-DESIGN.md` 和 L-033～L-035。

## 3. 变更流程

1. 新想法先进入 Roadmap 的 Backlog，不直接加入当前版本。

5. 未经确认的想法不得被 AI 自行扩展成实现范围。
