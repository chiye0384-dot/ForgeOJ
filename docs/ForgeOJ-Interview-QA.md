# ForgeOJ 面试问答骨架

> 当前状态：需求与 M-1 工程选型问答。  
> 下列答案解释已确认设计，不证明功能已经实现。涉及代码、性能和线上经历的问题，要等真实实现后补充证据，不能背诵虚构答案。

## 1. 项目介绍骨架

### 1.1 现在可以说的版本

ForgeOJ 是一个正在规划和开发的 Java 在线判题与小班教学平台。核心目标是在固定 Linux 环境中，用独立 Judge Worker 和受限 Docker 容器执行 Java 21 单文件代码，并通过 MySQL Outbox、RabbitMQ、幂等消费和死信处理保证异步判题可恢复；业务上包含公共题库、官方题解、班级作业、内容审核和独立管理员。当前已有 Spring Boot 4.1.1 / JDK 21 最小工程骨架，但业务实现尚未开始，不能把规划功能说成已经完成。

### 1.2 V1.0 完成后的 60 秒结构

1. 一句话说明用户和问题；
2. 说明一次提交的主链路；
3. 选择两个真实难点和对应验证；
4. 给出固定环境的真实数据；
5. 主动说明适用范围和一个限制。

具体数字、事故和优化结果必须从证据矩阵填入。

## 2. 产品与范围

### Q：为什么做 OJ，而不是更稳妥的点评或预约项目？

答：我希望项目能体现异步任务、容器隔离、状态机、幂等、权限和故障恢复，而不是只做 CRUD。OJ 的挑战更高，但我把范围限制在 Java 21、单文件和标准输入输出，不做多语言、竞赛和微服务，因此仍然是可以逐步理解和交付的难度。

### Q：这是不是照着 CodeJudge 改名？

答：不是。原简历项目只作为需求与面试深度的参考，ForgeOJ 有独立的角色、题目版本、班级作业、题解开放和管理员模型。工程起点只使用许可证已记录的 Spring Initializr 和 create-vue 最小生成骨架，没有引入外部 OJ 业务代码；判题域、Outbox、Worker 和沙箱链路都要由 ForgeOJ 自行设计和验证。

### Q：为什么不用 RuoYi 系或 JHipster 这类大型脚手架？

答：它们都有清楚的开源许可证，不是因为“不能用”。问题在于 ForgeOJ 当前只需要双进程和最小 Web/持久层起点，大型后台框架会同时带入权限、多租户、工作流、大量业务模块或生成器约定。删改、理解和解释这些内容的成本高于从官方最小骨架起步。

### Q：为什么用原生 MyBatis，不用 MyBatis-Plus？

答：我已经学过 MyBatis，而 ForgeOJ 的 Outbox、条件状态更新、任务领取和幂等逻辑需要显式理解 SQL 和并发条件。原生 MyBatis 的代码可能多一些，但不会为了复用脚手架被迫同时学习 MyBatis-Plus，也更容易在面试中说清楚真实 SQL。

### Q：PageHelper 很方便，为什么现在不加？

答：不是拒绝 PageHelper，而是延后到 M2 第一个真实分页列表出现时再加。M-1 还没有 Mapper 或分页 SQL，现在加依赖无法验证 `count`、复杂查询和页面边界。到真实需求出现时再用 Boot 4.1 兼容版本做集成测试，能得到真实证据。

### Q：为什么不一次把所有功能都做完？

答：最高风险是判题和沙箱，所以先做 M0 纵向切片，再逐步补可靠性、题库、班级和运维。题解社区放 V1.1，论坛和公开个人题单只是 V2 候选。这样每个阶段都能验收，不会同时留下大量半成品。

### Q：为什么不故意留几个问题给面试官问？

答：不会故意保留正确性或安全 Bug。可以讨论的内容来自真实边界和取舍，例如单机部署、只支持 Java 21、普通 Docker 不是绝对安全边界、ES 降级会失去全文检索。这些比故意制造缺陷更可信。

## 3. Java 21 与判题范围

### Q：“只支持 Java 21”是什么意思？

答：它主要指用户提交代码的编译和运行环境固定为 JDK 21，不是要求访问网站的用户电脑安装 JDK 21。代码在服务器的受限容器中编译运行。ForgeOJ 后端也使用 JDK 21，二者版本统一有利于学习和复现，但逻辑上是两个运行边界。

### Q：为什么选择 Java 21，而不是 Java 8、17 或 25？

答：Java 21 是长期支持版本，具有较新的语言和运行时能力，且在 Spring Boot 4.1.1 的官方支持范围内。后端与用户代码环境都固定为一个 LTS 版本，比同时维护多个 JDK 镜像更符合第一版范围。这里不是说其他版本不能做，而是当前项目主动减少兼容矩阵。

### Q：为什么只做 Main.java 和标准输入输出？

答：函数题需要代码模板生成、签名校验和包装器，多文件与第三方依赖还涉及构建和供应链风险。第一版先把不可信代码执行、消息可靠性和题目版本做正确。函数题可以作为后续独立设计，而不是伪装成一个简单开关。

### Q：为什么一份提交只编译一次，但每个测试启动新 JVM？

答：编译一次减少重复开销；每个测试新 JVM 避免静态变量、线程和全局状态污染后续测试。代价是进程启动增加延迟，所以必须在性能报告中分开记录容器、编译和运行耗时。

## 4. 隐藏测试与题解

### Q：为什么隐藏测试不能泄露？它又不是用户隐私。

答：它保护的是判题有效性，不是个人隐私。如果输入、正确输出、编号或通过数量被完整暴露，用户可以针对测试硬编码，而不是解决一般问题。系统可以展示编译错误和概括性结果，但不能泄露足以反推出隐藏数据的信息。

### Q：如果隐藏测试不能看，用户怎样学习正确解法？

答：隐藏测试和官方题解是两类数据。隐藏测试用于验证；正式题目必须有面向学习的官方题解。公共题的用户可以 AC 后自动解锁，也能在未 AC 时经防剧透确认主动查看；班级作业由教师选择立即、AC 后或截止后开放。

### Q：私有参考程序和官方题解有什么区别？

答：私有参考程序服务于出题和测试数据校验，普通用户永远看不到；官方题解服务于学习，需要包含思路和一份对当前 judge_version 验证 AC 的代码。两者不能混为同一份可公开资产。

### Q：用户发布题解后为什么不能直接修改代码？

答：题解标记为“已验证”的代码来自某次不可变 AC 提交。如果允许自由修改，修改后可能无法通过却仍显示已验证。用户要改代码，就从提交创建作答副本，重新提交并 AC，再替换题解来源；说明文字仍可自由编辑。

### Q：为什么题解标题不用 AI 生成？

答：需求只需要可靠兜底，确定性模板《题目名称》题解几乎不会失败，用户也可修改。引入 AI 会增加外部依赖、成本和失败路径，却没有足够收益。未来 Agent 项目会单独规划，不为技术名词强行接入。

## 5. 异步可靠性

### Q：为什么不用接口收到提交后直接发送 RabbitMQ？

答：数据库提交和消息发送不是同一个事务，会出现数据库成功但消息失败，或者消息发出后业务事务回滚。Outbox 让 Submission 和待发送事件在同一数据库事务落库，再由发布器可靠投递。它不消除重复消息，所以 Worker 仍必须幂等。

### Q：手动 ACK 为什么仍可能重复消费？

答：Worker 可能已经写入结果，但在 ACK 到达 RabbitMQ 前崩溃，消息会再次投递。这是至少一次投递的正常情况。应通过 judgeTaskId、状态条件更新和唯一约束让重复处理不产生第二个最终结果，而不是假设消息只来一次。

### Q：重试为什么不能创建一条新的用户提交？

答：用户只提交了一次。平台重试是同一个 judgeTask 的内部 attempt，如果创建新的 Submission，会伪造用户行为、改变尝试次数和作业统计。管理员只能触发可审计的内部幂等重试。

### Q：WebSocket 已经推送结果，为什么还需要轮询？

答：连接可能断开，推送也可能在页面切换时丢失。数据库才是最终事实来源，WebSocket 只降低感知延迟；轮询或重新查询保证用户最终能恢复到正确状态。

## 6. Docker 与安全

### Q：使用 Docker 就安全吗？

答：不等于绝对安全。V1 会使用非 root、禁网、只读根文件系统、能力删除、禁止提权、CPU/内存/PID/时间/输出限制，并让 API 与 Docker 权限分离，但仍只适合受控小范围试运行。更强威胁模型可能需要 gVisor、Firecracker 或独立判题节点。

### Q：为什么 API 服务不能直接操作 Docker？

答：Docker 控制权限非常敏感。把它放在同时处理公网业务请求的 API 中，会扩大攻击面。独立 Worker 只消费受控任务，API 消息中也不携带源码、隐藏测试或基础设施凭证，从而缩小权限范围。

### Q：怎样证明资源限制和清理真的有效？

答：不能只展示配置。要用无限循环、内存耗尽、进程爆炸、超量输出、联网和写文件等测试实际触发限制；随后检查结果分类、容器退出、临时文件、残留进程和监控指标。这些证据完成前不能宣称沙箱可靠。

## 7. 权限与管理员

### Q：OWNER、ASSISTANT、MEMBER 分别是什么？

答：它们是某一个班级内的角色。OWNER 管理班级和敏感操作；ASSISTANT 协助维护私有题、作业和相关进度，但不能管理所有权或其他助教；MEMBER 做题和完成作业。同一用户在不同班级可以拥有不同角色。

### Q：平台管理员为什么不直接使用普通用户角色？

答：平台管理员类似内容审核和运维人员，不是每个班级的老师。它们使用独立账号和后台：CONTENT_REVIEWER 审核公共内容，OPS_ADMIN 处理平台失败任务，SUPER_ADMIN 管理后台账号和角色。分离身份能减少越权与误操作，并使审计更清晰。

### Q：V1.0 管理员到底要做到什么才算完成？

答：不只是把角色名称写进数据库。要有独立登录、后端权限校验、公共题审核、异常任务和死信重试、管理员账号管理、审计日志，以及证明角色互相不能越权的自动化测试。普通用户访问后台接口必须返回 403。

### Q：管理员能把 WA 改成 AC 吗？

答：不能。管理员可以处理平台 SYSTEM_ERROR、死信和重试，但不能篡改用户源码或判题事实。题目或测试有错时，要暂停旧版本、建立修正版并标记历史影响，而不是手工改结果掩盖问题。

## 8. 班级和个人题单

### Q：为什么任何用户都能创建班级，不验证教师身份？

答：ForgeOJ 面向学习小组，不是学校教务系统。创建者是班级负责人，不代表学校认证教师。权限只在该班级内有效，这样既支持同学互助，也避免引入组织认证系统。

### Q：个人题单公开不就是多一个开关吗？为什么 V1 不做？

答：字段本身简单，公开后的完整产品责任不简单：需要明确发布授权、举报和下架、作者注销后的归属、题目失效后的展示，以及是否支持收藏、复制、搜索和个人主页。个人题单也能反映学习兴趣，因此 V1.0 与 V1.1 默认且仅私有。公开题单放到 V2 候选，若实现仍默认私有、由用户主动发布，并允许取消公开。

### Q：为什么官方题单是公开的，个人题单却私有？

答：官方题单是平台审核和维护的公共学习路径；个人题单是用户自己的学习计划与收藏。二者的责任、隐私预期和失效处理不同，不应该因为数据结构相似就采用相同发布规则。

## 9. Redis、Elasticsearch 与一致性

### Q：为什么既用 Redis 又用 Elasticsearch？

答：它们解决不同问题。Redis 服务于热点缓存、会话、限流和短期去重；ES 服务于公共题面全文检索、筛选和高亮。MySQL 保存权威数据，二者都可以失效、降级或重建。

### Q：Redis 挂了还能登录吗？

答：设计上会回查 MySQL 的权威会话记录，绝不能因为 Redis 故障就跳过封禁和会话失效检查。性能会下降、限流会转为更保守策略，但安全判断不能放行。

### Q：ES 中为什么不索引班级私有题？

答：一旦私有内容进入共享搜索索引，过滤配置错误或查询漏洞就可能泄露题目。V1 只索引公共字段，ES 返回候选 ID 后还要由 MySQL 复核公开状态。私有题使用数据库范围内查询，牺牲部分搜索能力换取边界清晰。

## 10. 部署、上线和真实性

### Q：部署到 Linux 是上线吗？

答：Linux 部署是环境验收；只有云服务器可被受控真实用户访问并承担一段时间运维，才适合称小范围上线。两者都不能被夸大为大规模生产系统。项目会优先在固定 Linux 环境完成验收，再部署阿里云等云主机进行邀请制试运行。

### Q：为什么不一开始就买阿里云服务器？

答：M0 判题链路和资源需求尚未验证，过早购买可能选错配置并浪费优惠。先在可控 Linux 环境跑通，接近 V1.0 时根据真实 CPU、内存、磁盘和并发数据选择云资源。

### Q：面试官问“有没有上线”该怎样回答？

答：按事实分级回答：只在本地运行、在 Linux 验收、在云端部署、还是有少量真实用户试用。说明时间、规模、遇到的问题和监控/恢复证据；没有真实用户就不要说有用户，没有长期运维就不要说稳定运营。

### Q：性能数字怎样写才可信？

答：普通 Web API 用 req/s 和延迟；判题用 submissions/min、排队、编译、运行和端到端耗时；消息链路关注投递延迟、丢失和重复副作用。所有结果记录机器、数据集、脚本、时长、错误率、资源占用和 commit。不能复制参考项目的数字。

## 11. 实现后必须补齐的真实问题

以下问题现在只能保留骨架，不能预编答案：

- 实际最难定位的 Bug 是什么，根因和修复是什么；
- Worker 在哪个阶段发生过真实故障；
- 第一轮压测的瓶颈在哪里；
- 做过什么优化，前后数据是否可复现；
- 阿里云实际配置、试运行规模和运行时长；
- 恢复和回滚演练用了多久；
- 真实用户最常反馈什么；
- 哪个设计在实现后被推翻，为什么。

这些问题要从 issue、commit、测试和报告中回答，不从想象中补全。

## 12. 项目掌握度练习

每完成一个里程碑，都要练习：

1. 用 60 秒和 3 分钟各介绍一次；
2. 从页面请求追到数据库、消息和 Worker；
3. 根据 submissionId 定位一次失败；
4. 解释一个被拒绝的替代方案；
5. 修改一个小规则并补测试；
6. 故障注入后恢复服务；
7. 指出至少一个仍存在的真实限制。

如果只能背结论、不能定位代码和验证，就还不能把该能力写进简历。
