# ForgeOJ 性能与可靠性测试计划

> 完整计划状态：`IN_PROGRESS`。
> 当前没有任何可写入简历的 QPS、P95、吞吐或优化比例。

## 1. 目标

本计划回答三个问题：

1. 固定 Linux 环境下，系统在什么负载范围内表现稳定；
2. 瓶颈位于 Web API、数据库、缓存/搜索、消息排队还是 Docker 判题；
3. 优化前后的差异能否在相同条件下复现。

性能测试不用于模拟百万用户，也不把不同性质的指标合成一个“ForgeOJ 总 QPS”。

## 2. 测试前置条件

每份报告必须记录：

- 报告 ID、日期和测试人员；
- Git commit、release/tag 和工作树状态；
- Linux 发行版与内核；
- CPU 型号、核数、内存、磁盘类型；
- Docker、JDK 和各中间件版本；
- API/Worker 实例数和 Worker 并发；
- 每个容器的 CPU、内存和 PID 限制；
- 数据集版本、题目数、用户数和提交历史量；
- Java 判题镜像 digest；
- 测试脚本 commit；
- 预热方式、并发模型和持续时间；
- 是否冷缓存、是否冷容器；
- 网络位置和 HTTPS 是否启用。

缺少这些条件的数字只能用于临时诊断，不能进入简历。

## 3. 数据集

建立可重复生成的脱敏数据集，至少包含：

- 不同难度和标签的公共题；
- 官方题单与用户私有题单；
- 多个班级、成员和作业；
- 足够数量的历史提交；
- 标题和题面中具有明确检索词的题目；
- 判题样例：快速 AC、WA、CE、RE、TLE、MLE、OLE；
- 短、中、长三档测试输入；
- 固定可校验的期望结果。

数据生成脚本必须版本化。不得使用真实用户邮箱、密码或源码。

## 4. 指标分类

### 4.1 Web API

- 请求吞吐量；
- P50、P95、P99 响应时间；
- 错误率和超时率；
- API CPU、内存、线程和数据库连接池；
- MySQL 查询延迟和慢查询。

典型接口：登录、公共题列表、题目详情、题单进度、提交记录和作业进度。

### 4.2 Redis

- 缓存命中与未命中延迟；
- 命中率；
- 热点 key 重建时的数据库压力；
- Redis 故障时的回退延迟、错误率和数据库负载；
- 限流与会话检查在故障下是否保持安全。

### 4.3 Elasticsearch

- 全文检索 P50/P95/P99；
- 搜索吞吐和错误率；
- Outbox 到索引可见的延迟；
- ES 故障后的熔断时间和 MySQL 回退表现；
- 全量重建耗时及重建期间可用性。

### 4.4 提交接收与消息链路

- 提交接口响应时间；
- 业务事务到 Outbox 可发布时间；
- Outbox 到 RabbitMQ 的投递延迟；
- 队列深度与消息驻留时间；
- 重复投递数量；
- 丢失提交数；
- 重复业务副作用数；
- 重试与死信数量。

这里的目标首先是正确性：已由 API 成功接收的正式提交不能静默丢失，重复消息不能产生第二份最终业务结果。

### 4.5 判题计算链路

- 每分钟完成的提交数；
- 排队时间；
- 拉取任务到容器启动时间；
- 编译时间；
- 各测试运行时间；
- 容器清理时间；
- 端到端 P50/P95/P99；
- Worker CPU、内存、并发和失败率；
- 残留容器与临时文件数。

判题吞吐必须注明题目、用例、代码和冷/热条件，不能与普通 API 的 req/s 比较。

### 4.6 结果通知

- 写入最终结果到 WebSocket 到达的延迟；
- 推送成功率；
- 主动断开或丢失推送后，轮询恢复最终结果的成功率和时间；
- 重连时是否出现重复或倒退状态。

## 5. 测试类型

### 5.1 基线测试

在低到中等固定负载下运行，获得尚未优化时的延迟、吞吐和资源曲线。不得丢弃“不好看”的第一次真实基线。

### 5.2 阶梯加压

逐级提高并发，每一级保持足够时间，观察：

- 延迟何时明显上升；
- 错误率何时出现；
- 数据库连接池、队列或 Worker 何处饱和；
- 停止加压后能否恢复。

容量边界由测试数据确定，不预先写漂亮目标。

### 5.3 突发测试

短时间制造提交峰值，验证限流、每用户排队上限、队列保护和页面状态是否正确。系统可以拒绝超出能力的请求，但不能静默丢失已经接受的提交。

### 5.4 长稳测试

持续运行以观察：

- 内存、线程和连接是否增长；
- Docker 容器与临时文件是否残留；
- Outbox 是否长期积压；
- Redis/ES/MySQL 磁盘和内存趋势；
- WebSocket 连接是否泄漏。

持续时长由机器预算确定，但报告必须写明，不能把短测称为稳定性测试。

### 5.5 故障恢复测试

逐项故障，不同时制造所有故障：

- 暂停 Redis；
- 暂停 Elasticsearch；
- 暂停 RabbitMQ；
- 在任务处理的不同阶段终止 Worker；
- 让 Docker 执行失败；
- 模拟 WebSocket 断线；
- 制造数据库短时不可用（仅在隔离测试环境）。

记录故障开始、检测、降级、恢复和积压清空时间，以及是否发生数据错误。

### 5.6 优化回归

只有先定位瓶颈，才做优化。优化报告必须包含：

1. 原始症状和观测证据；
2. 假设；
3. 单一或可解释的改动；
4. 相同环境下的前后测试；
5. 正确性回归；
6. 改善、无变化或退化的完整结果；
7. 新引入的代价。

## 6. 执行顺序

1. 先验证功能正确性和测试数据；
2. 再测只读普通 API；
3. 再测 Redis/ES 正常与降级；
4. 再测提交接收和消息可靠性；
5. 最后测最昂贵的 Docker 判题链路；
6. 做长稳和故障恢复；
7. 根据数据选择是否优化；
8. 相同条件回归。

不要在云服务器资源不足时用高压测试影响同机真实试用数据；压测使用隔离环境或维护窗口。
